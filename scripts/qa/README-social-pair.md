The runner unwraps the backend `{ "ok": true, "data": ... }` response, validates the complete API readiness body (database, migrations and Redis), selected devices, and distinct authenticated A/B identities. The manifest contains SHA, branch, dirty flag, ports, tool versions, device identifiers and sanitized API observations; it contains no tokens or raw API responses. Default output is `scripts/qa/evidence/runs/<runId>/manifest.json`.

Keep barriers and screenshot/media artifacts separate; the runner retains barrier markers with the evidence. The runner writes the expected actor ID for every role and a fresh `invocationId` into the private barrier metadata; a role whose authenticated ID does not match its assignment is rejected before arrival. Use a short fixed `name` such as `decisions-submitted` or `foreground-check` for each synchronization point, and keep `timeout` bounded. Markers are atomically created, include run/case/role/actor/invocation identity, and cannot be overwritten by a duplicate role; a missing peer raises `TimeoutError`, and a stale or mismatched marker fails closed. The default barrier wait is 90 seconds; the runner allows 180 seconds for a driver process. Drivers with sequential waits should use one shared deadline and pass only its remaining time to each wait. Do not create your own shared marker paths or clean up the runner's barrier directory.

`H7.S4.M3-A_IOS.py` runs two Maestro flows on the assigned simulator. It checks the app's visible profile email against A's `/auth/me` identity before opening the exact pair conversation. It sends `H7.S4.M3 <runId> <invocationId> original`, then waits at `initial-visible` so B_WEB can prove that original text before A edits it to `... edited`. Maestro targets the row by its `chat-message-edit-<messageId>` test ID, verifies the edited label and persisted `editedAt` on that same ID, captures its own screenshot, joins `edited-visible`, and deletes only that fixture message. Both roles publish atomic markers with the same `invocationId`; each side rejects a marker from another invocation. Generated Maestro files and logs are private temporary files removed after the role exits. The chat composer exposes `Escribe un mensaje` / `Editar mensaje actual` for the input and `Enviar mensaje` / `Guardar edición` for its action.

`H7.S4.M3-B_WEB.py` is the Playwright observer for the web half of message editing. It requires the assigned A/B actors to already be an accepted connection; it only starts/gets their exact pair conversation and never changes the relationship. B waits for A's run-and-invocation-marked message, verifies the original and edited text through the UI and API, and captures its own screenshot under one 150-second deadline. The per-invocation nonce prevents old fixture messages from satisfying a later run that reuses `runId`. A missing accepted connection exits 2 before a message is written, which the runner records as `BLOCKED`.

H7.S4.M5 irreversibly deletes the accepted connection and revokes every active direct chat for that pair. It cannot restore prior messages, and there is no cleanup route for the revoked records. Run it only against a reserved QA pair with disposable data; do not use shared or human conversations. The runner requires the separate M5 ACK and both reserved UUIDs before launching a role. Both roles finish API and media preflight before either opens the conversation UI. A verifies the reserved conversation and visible text+image fixtures; B verifies that conversation is the pair's only active direct chat and that the exact connection is the pair's only accepted connection. B then calls the authenticated connection DELETE endpoint once, and both actors verify history and image access return 404. B also verifies the reserved connection disappears. If any precondition is missing, no disconnect is sent. Never retry by recreating or reconnecting the pair after the DELETE succeeds. B_WEB currently triggers the existing API endpoint and observes the resulting closed chat in the web UI; the current web community UI does not expose a disconnect action for accepted connections.

`H7.S4.M1` uses the exact reserved A/B conversation and verifies its `otherUserId` matches B's authenticated actor. It first checks that the visible app profile matches A's `/auth/me` identity. Only after API, device, app-installation, and conversation checks pass does the driver revoke Android `RECORD_AUDIO` and set `user-fixed`; it verifies Android reports `denied` and that `dumpsys package` contains the `USER_FIXED` flag. Maestro checks the alert text, captures it, dismisses it, enters a run-marked draft, captures the available text composer, then erases the local draft without sending. Both screenshots are stored with mode `0600`. The permission remains permanently denied on the acknowledged disposable device after the run, including if the UI assertion fails. The driver does not send a message or create server data.

M4 requires `QA_DISPOSABLE_CONVERSATION_ID` to equal the exact assigned A/B conversation before any settings mutation. The selected read-receipt override is persistent. The API can restore the prior effective boolean, but cannot restore whether it was inherited (`null`) or its prior `read_receipts_enabled_since` cutoff; `ALL` resets unrelated conversation overrides and is forbidden for cleanup. Keep M4 blocked unless the QA account and pair are dedicated to this test and the changed cutoff is acceptable. Never run M4 or M5 against shared or human conversations.

`H7.S4.M4` has A_ANDROID/A_IOS observers, A_WEB as the sole preference writer, and B_WEB as the sender/receipt observer. All roles resolve the existing reserved conversation from their own `/me/conversations` list; they do not create a chat. The four drivers have helper/syntax tests; runtime acceptance still requires the live QA API/web, the reserved fixture, and both native devices.

The web role uses Node 20–23 and the repository's installed Playwright package. Set `QA_NODE_PATH` if the compatible Node binary is not on `PATH`; the wrapper checks the version before launching Chromium. The token is inherited only by the role process and is never placed in a command argument or browser page script.

Exit 2 means `BLOCKED`, exit 1 means `FAIL` or invalid invocation, and exit 0 means all selected cases passed these gates. A driver may use exit 2 only for a required precondition it detects before mutating data; other nonzero exits are failures.
